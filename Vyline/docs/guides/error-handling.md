# エラー表示と復旧方針

最終更新: 2026-11-06

ユーザーが開始した操作の失敗は、操作場所に近い固定高さの `ActionFeedback` か、操作結果に結び付いたメッセージで説明する。失敗時は「何が完了しなかったか」「安全な次の操作」を示し、通信切断など結果が確定しない送信は失敗と断定しない。

## 表示・記録の境界

- API境界では内部例外を安定したエラーコードと利用者向けメッセージへ変換する。
- トークン、復号鍵、ローカルパス、SQL、メッセージ本文、スタックトレースをAPI応答や画面へ含めない。
- 調査が必要な処理は、秘密情報を含み得る元例外ではなく、許可されたコード・段階だけをログへ記録する。
- 背景ポーリング、任意キャッシュ、パーサーの代替経路は、利用者の操作を妨げない既知のフォールバックである場合に限り静かに継続できる。失敗状態を無期限に成功扱いしない。
- 定期処理の失敗を繰り返し画面へ通知しない。必要なら接続状態や診断ログへ集約する。

## Desktop履歴の復元

設定 > 詳細・復元からの履歴取り込みは、`DESKTOP_RESTORE_*` コードと `stage` を返す。プロセス検出、復号鍵の走査・照合、DB整合性検査、アカウント照合、取り込みのどこで止まったかを示し、ローカルDBやプロセスメモリの内容は返さない。

GitHub Issue #408 の添付診断イベントは報告された復元操作より前の日付で、履歴取り込みAPIへの要求も含んでいなかった。その添付だけでは失敗原因を特定できない。更新後に再現した場合は、画面に出るコードと段階を使って切り分ける。

## UI実装

`apps/desktop/src/components/action-feedback.tsx` の `ActionFeedback` を操作ボタンの近くへ置く。空の状態でも最小高さを保ち、`aria-live` で結果を通知する。長文は折り返し、エラー出現時に主要操作が飛び跳ねないようにする。

新しいユーザー操作では成功・失敗・通信切断の結果を確認し、意図的に静かにするcatchは理由を近くに記す。すべての `catch` を機械的に通知へ置き換えない。
